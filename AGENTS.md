## Sharp edges

- `node_modules/` is **no longer committed** (ignored and untracked as of scraper-109): run `npm install` on a fresh checkout, and the Docker build installs dependencies itself before `npm run build`. A pre-existing checkout may still carry a `sqlite3` native binding built for a different platform (the docker deployment targets Linux x86-64); on such a host every module that reaches `require("sqlite3")` fails to load, so the scraper test suites (`tests/jooble.test.ts`, `tests/kitalulus.test.ts`, ...) cannot run there until the binding is rebuilt locally.
- The per-portal SQLite files under `db/` are likewise runtime-created, git-ignored, and excluded from Docker images: the scoring Supabase's unique-constraint upserts are the dedupe authority, and a legacy portal starting from an empty local database may re-POST previously seen applicants to `api_destination` once (see `db/README.md`).
- Because of the above, code that needs SQLite should load it lazily and sit behind an interface. `src/central/store.ts` is that interface; `LocalStore` is the SQLite implementation and `InMemoryStore` the portable one, and `tests/central/localStore.test.ts` runs the same contract against both (skipping the SQLite half when the binding will not load).
- The scrapers build their SQL by string interpolation. Anything new should use bound parameters, as `src/central/localStore.ts` does.
- The `dockerfile` base image tag must stay pinned to the exact `playwright` version in `package-lock.json` (pairing rule in the dockerfile header, enforced by `tests/dockerfile-playwright.test.ts`); a floating tag put production in a launch-fail crash loop. The production (Dokploy) container entrypoints are the continuous `xvfb:<portal>` commands (see "Direct scoring sink" below).
- The pinned playwright image also freezes its **bundled Node**, which can be older than what dependencies need (v1.44.0-jammy ships a pre-20.16 Node; `pdf-parse@2`/`pdfjs-dist` need >= 20.16 / 22.3 and crashed production at module load). The dockerfile therefore overlays its own pinned Node (`ARG NODE_VERSION`, before `npm ci` so native modules build against it), and `tests/dockerfile-playwright.test.ts` asserts that version against every `engines.node` range in the lockfile. Bump `NODE_VERSION` when a new dependency raises the floor. The overlaid Node also has no prebuilt sqlite3 binding, so the dockerfile installs `build-essential` before `npm ci` (same test guards the ordering) — dropping it makes the image build die at node-gyp with "not found: make".
- `src/server.ts` loads portal modules and configs **lazily** per dispatched command (`buildPortalRunner` / `continuousScraperFactories`), so one portal's broken dependency cannot crash another portal's container; `tests/serverLazyPortals.test.ts` proves every portal's runner graph stays clean of the other portals, of eagerly loaded sqlite3, and (except kitalulus, which OCRs CVs) of pdf-parse. Keep new portal wiring inside those factory maps, never as top-level imports. Boot prints one `[boot] node ... | playwright ... | command ...` line for runtime-mismatch triage.

## Portal scraper retries

- `src/server.ts` runs every portal command through `runWithRetry` (`src/retry.ts`), so a failed Playwright scrape is retried with exponential backoff and the process exits non-zero only once the attempt budget is spent. Each attempt constructs a **fresh** scraper instance; scraper objects carry per-run state (DB handle, `COLLECTED`) and must not be reused across attempts.
- The scrapers only call `browser.close()` on the happy path. Any new `playwright.*.launch(...)` must therefore be wrapped in `trackBrowser(...)` (`src/browserRegistry.ts`), which is how a failed attempt closes the leftover browser before the next one starts.

## Central Supabase ingestion

- `src/central/` mirrors scraped candidates, vacancies and applications into a central Supabase database on top of the per-portal SQLite files in `db/`. It talks PostgREST over axios rather than adding a Postgres driver. See the "Central Supabase Ingestion" section of `README.md` for setup and the runner commands, `.env.sample` for configuration, and `migrations/0001_central_ingestion.sql` for the schema and the `cross_check_idrkos_candidate` function.
- Scrapers hook in through `src/central/portalBridge.ts`, called right after their existing local insert. The bridge swallows its own failures on purpose: a central problem must never abort a scraping run, since the local outbox already holds the row.
- Candidates are the one entity that is **not** pushed synchronously: `src/central/talentStream.ts` batches them into `talent_scraping` and settles the outbox row afterwards, so `IngestResult.pushed_to_central` is false right after `ingestCandidate` and `queued_for_central` is what the caller sees. Anything that asserts on the central write must `await service.flushStream()` (or `flushIngestionStream()`) first; `src/server.ts` drains through `closeIngestionService()` when a portal run ends.

## Direct scoring sink

- Every portal except kitalulus-v2 (glints, jooble, seek, pintarnya, kitalulus v1 — v1 is the live kitalulus variant) bypasses the legacy `api_destination` and native SQLite path through `src/supabaseSink.ts`. The self-hosted `scrape` and cloud-compatible `talent_scraping` schemas are managed under `atlas/`; follow `atlas/README.md` for generation, validation, baseline, and Storage setup.
- The shared slice is `src/portalSink.ts` (`sendApplicantToSink`): identity ladder via `src/candidateIdentity.ts`, write-once upserts, and canonical `data` keys (`work_experience`/`education`/`skill`/`contact.contact_number`/`date_of_birth`/`location`). The DB-side `talent_scraping` projection reads exactly those spellings, so new portals normalize their field names client-side in their `sendToSink` instead of teaching the projection per-portal shapes. Each portal keeps its deprecated `sendRequest` (legacy api_destination + SQLite + central mirror) present but bypassed.
- One Dokploy container per portal: `xvfb:<portal>` runs the continuous loop (`<portal>-continuous` in `src/server.ts`, per-cycle `scrape.scrape_runs` row via `runPortalCycle`), `xvfb:<portal>:once` a single run. An expired portal session throws one loud `[PORTAL] Session expired ...` line, fails that cycle, and the loop keeps cycling — do not refresh sessions in code except through the credential-login seam in the next bullet (currently Glints only).
- Rows reference artifacts by **bucket object key only** (`cv_object_key`/`photo_object_key` columns and the `data.cv`/`data.photo` spellings) — never by a scraper-host filesystem path; local downloads are temp files deleted right after upload. Glints' contact/email/CV/applicant-id come primarily from the dashboard's own `GET /api/jobs/{jobId}/applications/{applicationId}` response captured on modal open (`armApplicationDetailCapture`/`parseGlintsApplicationDetail` in `src/glints.ts`), with the modal's "Kontak Pelamar" block as DOM fallback; the CV replays the dashboard's `GET /api/s3/download?key={resume}&label=resume` — all passive reads, no pipeline-stage changes (never adopt the legacy `MoveApplicant` "Dalam Komunikasi" flow for data capture without explicit authorization). Glints gates contact+CV on un-progressed ("BARU") applications: both API and modal then serve mask literals (`+62****`, `****@****`), which `stripGlintsContactMask` collapses to "" so gated rows keep clean empties (full contact appears only once a human progresses the application).
- The Glints account manages **two** companies; applicants live under "PT Rajawali Berdikari Indonesia" (the "PT RADIKARI" entry has none). `glints.json` `target_company` must be one of the switcher's *display* strings — `selectTargetCompany` (`src/glints.ts`) matches trim/case-insensitively, logs the entries seen, and throws naming them on a non-match. The scraper pins the browser locale to `id-ID` because its text anchors assume the Indonesian dashboard.
- Glints self-renews its session: when the replayed `glints.json` export is dead, the scraper logs in with the `GLINTS_EMAIL`/`GLINTS_PASSWORD` env credentials (runtime secrets, masked in all logs/errors) and keeps the refreshed cookies+localStorage in process memory (`glintsSessionStore`) — never on disk. When `SCORING_SUPABASE_SERVICE_KEY` is set, every successful authentication is also persisted to the private bucket object `glints/session/current.json` and restored on boot (memory → bucket → `glints.json` warm-start), so a container restart replays the trusted session instead of re-logging-in. The portal-agnostic pieces (credential loading, masking, attempt-cap guard, in-memory + bucket session stores) live in `src/portalLogin.ts` for other portals to adopt; the cap guard is module-level in `src/glints.ts` because the loop builds a fresh scraper per attempt. `GLINTS_LOGIN_FAILED` / `GLINTS_LOGIN_CHALLENGE` / `GLINTS_LOGIN_OTP_REQUIRED` log lines are the triage markers; a challenge still means a human session export (kitalulus/pintarnya instead read credentials from their committed JSON configs — do not copy that pattern for new secrets). Any login outcome the classifier cannot name self-documents: `captureLoginDebugArtifacts` (`src/portalLogin.ts`) uploads screenshot + password-masked HTML + meta to `scrape-artifacts` under `<portal>/login-debug/<timestamp>/` (the `LOGIN_DEBUG_ARTIFACTS` log line carries the paths), so triage a server-only login failure from the bucket, not by guessing.
- Glints device verification is a first-class login state: from an untrusted device (the server) the credential submit lands on the "Verifikasi diri Anda" interstitial (`device_verification` in `classifyGlintsLoginResult`, detected by the `send-email/whatsApp-verification-btn` data-cy buttons). The scraper clicks the EMAIL option only — never WhatsApp — then opens a row in `scrape.glints_verification` (service-key-only table, atlas-managed), logs `GLINTS_VERIFICATION_CODE_NEEDED (… row <id>)`, and polls that row for 10 minutes for a human to `UPDATE … SET code='…'`. The code page submits through its **own** button, `[data-cy="otp-verify-btn"]` ("Verifikasi", `GLINTS_VERIFICATION_SUBMIT_SELECTOR`, text-locator fallback) — it has no `button[type="submit"]`, so reusing the credential-login submit selector there silently typed the code and never sent it, mis-settling correct codes as `rejected`; never click the sibling `otp-resend-button-btn`/`otp-back-btn`. Code emails are capped at one per 30 minutes via the row timestamps (durable across restarts); a verification wait or timeout is NOT a failed login attempt, so the cycle keeps re-entering the flow without burning the credential budget. A legacy `otp_required` classification (code input already rendered, or a verification route) still parks the whole budget.
- The direct sink path deliberately does **not** mirror rows into the central Supabase ingestion: `src/central/portalBridge.ts` stays wired only to the legacy SQLite insert path. Do not re-add `ingestPortalApplicant`/`ingestPortalVacancy` calls to the sink path.
- The mirrored `talent_scraping` tables are populated database-side: a SECURITY DEFINER trigger on `scrape.portal_candidates` (`atlas/migrations/20260818090000_project_talent_scraping.sql`) projects each candidate write. Client code never touches the `talent_scraping` schema and anon has no grants there — do not add client-side writes to it.
