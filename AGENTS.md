# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.

## Sharp edges

- `node_modules/` is **no longer committed** (ignored and untracked as of scraper-109): run `npm install` on a fresh checkout, and the Docker build installs dependencies itself before `npm run build`. A pre-existing checkout may still carry a `sqlite3` native binding built for a different platform (the docker deployment targets Linux x86-64); on such a host every module that reaches `require("sqlite3")` fails to load, so the scraper test suites (`tests/jooble.test.ts`, `tests/kitalulus.test.ts`, ...) cannot run there until the binding is rebuilt locally.
- The per-portal SQLite files under `db/` are likewise runtime-created, git-ignored, and excluded from Docker images: the scoring Supabase's unique-constraint upserts are the dedupe authority, and a legacy portal starting from an empty local database may re-POST previously seen applicants to `api_destination` once (see `db/README.md`).
- Because of the above, code that needs SQLite should load it lazily and sit behind an interface. `src/central/store.ts` is that interface; `LocalStore` is the SQLite implementation and `InMemoryStore` the portable one, and `tests/central/localStore.test.ts` runs the same contract against both (skipping the SQLite half when the binding will not load).
- The scrapers build their SQL by string interpolation. Anything new should use bound parameters, as `src/central/localStore.ts` does.
- The `dockerfile` base image tag must stay pinned to the exact `playwright` version in `package-lock.json` (pairing rule in the dockerfile header, enforced by `tests/dockerfile-playwright.test.ts`); a floating tag put production in a launch-fail crash loop. The production (Dokploy) container entrypoints are the continuous `xvfb:<portal>` commands (see "Direct scoring sink" below).
- The pinned playwright image also freezes its **bundled Node**, which can be older than what dependencies need (v1.44.0-jammy ships a pre-20.16 Node; `pdf-parse@2`/`pdfjs-dist` need >= 20.16 / 22.3 and crashed production at module load). The dockerfile therefore overlays its own pinned Node (`ARG NODE_VERSION`, before `npm ci` so native modules build against it), and `tests/dockerfile-playwright.test.ts` asserts that version against every `engines.node` range in the lockfile. Bump `NODE_VERSION` when a new dependency raises the floor. The overlaid Node also has no prebuilt sqlite3 binding, so the dockerfile installs `build-essential` before `npm ci` (same test guards the ordering) — dropping it makes the image build die at node-gyp with "not found: make".
- `src/server.ts` loads portal modules and configs **lazily** per dispatched command (`buildPortalRunner` / `continuousScraperFactories`), so one portal's broken dependency cannot crash another portal's container; `tests/serverLazyPortals.test.ts` proves every portal's runner graph stays clean of the other portals, of eagerly loaded sqlite3, and (except kitalulus, which OCRs CVs) of pdf-parse. Keep new portal wiring inside those factory maps, never as top-level imports. Boot prints one `[boot] node ... | playwright ... | command ...` line for runtime-mismatch triage.

## Portal scraper retries

- `src/server.ts` runs every portal command through `runWithRetry` (`src/retry.ts`), so a failed Playwright scrape is retried with exponential backoff and the process exits non-zero only once the attempt budget is spent. Each attempt constructs a **fresh** scraper instance; scraper objects carry per-run state (DB handle, `COLLECTED`) and must not be reused across attempts.
- The scrapers only call `browser.close()` on the happy path. Any new `playwright.*.launch(...)` must therefore be wrapped in `trackBrowser(...)` (`src/browserRegistry.ts`), which is how a failed attempt closes the leftover browser before the next one starts.

## Central Supabase ingestion

- `src/central/` mirrors scraped candidates, vacancies and applications into a central Supabase database on top of the per-portal SQLite files in `db/`. It talks PostgREST over axios rather than adding a Postgres driver. See the "Central Supabase Ingestion" section of `README.md` for setup and the runner commands, `.env.sample` for configuration, and `migrations/0001_central_ingestion.sql` for the schema and the `cross_check_idrkos_candidate` function.
- Scrapers hook in through `src/central/portalBridge.ts`, called right after their existing local insert. The bridge swallows its own failures on purpose: a central problem must never abort a scraping run, since the local outbox already holds the row.
- Candidates are the one entity that is **not** pushed synchronously: `src/central/talentStream.ts` batches them into `talent_scraping` and settles the outbox row afterwards, so `IngestResult.pushed_to_central` is false right after `ingestCandidate` and `queued_for_central` is what the caller sees. Anything that asserts on the central write must `await service.flushStream()` (or `flushIngestionStream()`) first; `src/server.ts` drains through `closeIngestionService()` when a portal run ends.

## Direct scoring sink

- Every portal except kitalulus-v2 (glints, jooble, seek, pintarnya, kitalulus v1 — v1 is the live kitalulus variant) bypasses the legacy `api_destination` and native SQLite path through `src/supabaseSink.ts`. The self-hosted `scrape` and cloud-compatible `talent_scraping` schemas are managed under `atlas/`; follow `atlas/README.md` for generation, validation, baseline, and Storage setup.
- The shared slice is `src/portalSink.ts` (`sendApplicantToSink`): identity ladder via `src/candidateIdentity.ts`, write-once upserts (existing candidate rows additionally take a fill-empty-only contact backfill on re-scrape — masked-then-unmasked contacts, e.g. Glints TERHUBUNG; see `SupabaseSink.upsertCandidate`), and canonical `data` keys (`work_experience`/`education`/`skill`/`contact.contact_number`/`date_of_birth`/`location`). The DB-side `talent_scraping` projection reads exactly those spellings, so new portals normalize their field names client-side in their `sendToSink` instead of teaching the projection per-portal shapes. Each portal keeps its deprecated `sendRequest` (legacy api_destination + SQLite + central mirror) present but bypassed.
- One Dokploy container per portal: `xvfb:<portal>` runs the continuous loop (`<portal>-continuous` in `src/server.ts`, per-cycle `scrape.scrape_runs` row via `runPortalCycle`), `xvfb:<portal>:once` a single run. An expired portal session throws one loud `[PORTAL] Session expired ...` line, fails that cycle, and the loop keeps cycling — do not refresh sessions in code except through the credential-login seam in the next bullet (currently Glints only).
- Rows reference artifacts by **bucket object key only** (`cv_object_key`/`photo_object_key` columns and the `data.cv`/`data.photo` spellings) — never by a scraper-host filesystem path; local downloads are temp files deleted right after upload. Glints' contact/email/CV/applicant-id come primarily from the dashboard's own `GET /api/jobs/{jobId}/applications/{applicationId}` response captured on modal open (`armApplicationDetailCapture`/`parseGlintsApplicationDetail` in `src/glints.ts`), with the modal's "Kontak Pelamar" block as DOM fallback; the CV replays the dashboard's `GET /api/s3/download?key={resume}&label=resume` — all passive reads, no pipeline-stage changes (never adopt the legacy `MoveApplicant` "Dalam Komunikasi" flow for data capture without explicit authorization). Glints gates contact+CV on un-progressed ("BARU") applications: both API and modal then serve mask literals (`+62****`, `****@****`), which `stripGlintsContactMask` collapses to "" so gated rows keep clean empties (full contact appears only once a human progresses the application). To capture the unmasked contacts *without* the scraper progressing anyone, the vacancy loop iterates `GLINTS_PIPELINE_STAGES` (`src/glints.ts`) per vacancy — currently BARU (the default view) plus TERHUBUNG (the "Connected" stage a human has already moved the applicant to). Stage tabs are filter-only: `selectPipelineStage` clicks the stage-tab button by its id+en text (`Terhubung`/`Connected`) which never moves an applicant; the modal-detail anchor is the stage's own `modalBadgePattern` (matches BARU's `Belum Sesuai|NEW` and TERHUBUNG's `Terhubung|Connected`) so the same extractors work across stages. Add a new stage by appending one entry to `GLINTS_PIPELINE_STAGES`; never introduce a click that transitions an applicant between stages.
- The Glints account manages **two** companies; applicants live under "PT Rajawali Berdikari Indonesia" (the "PT RADIKARI" entry has none). `glints.json` `target_company` must be one of the switcher's *display* strings — `selectTargetCompany` (`src/glints.ts`) matches trim/case-insensitively, logs the entries seen, and throws naming them on a non-match. The scraper pins the browser locale to `id-ID` because its text anchors assume the Indonesian dashboard.
- Glints self-renews its session: when the replayed `glints.json` export is dead, the scraper logs in with the `GLINTS_EMAIL`/`GLINTS_PASSWORD` env credentials (runtime secrets, masked in all logs/errors) and keeps the refreshed cookies+localStorage in process memory (`glintsSessionStore`) — never on disk. When `SCORING_SUPABASE_SERVICE_KEY` is set, every successful authentication is also persisted to the private bucket object `glints/session/current.json` and restored on boot (memory → bucket → `glints.json` warm-start), so a container restart replays the trusted session instead of re-logging-in. The portal-agnostic pieces (credential loading, masking, attempt-cap guard, in-memory + bucket session stores) live in `src/portalLogin.ts` for other portals to adopt; the cap guard is module-level in `src/glints.ts` because the loop builds a fresh scraper per attempt. `GLINTS_LOGIN_FAILED` / `GLINTS_LOGIN_CHALLENGE` / `GLINTS_LOGIN_OTP_REQUIRED` log lines are the triage markers; a challenge still means a human session export (kitalulus/pintarnya instead read credentials from their committed JSON configs — do not copy that pattern for new secrets). Any login outcome the classifier cannot name self-documents: `captureLoginDebugArtifacts` (`src/portalLogin.ts`) uploads screenshot + password-masked HTML + meta to `scrape-artifacts` under `<portal>/login-debug/<timestamp>/` (the `LOGIN_DEBUG_ARTIFACTS` log line carries the paths), so triage a server-only login failure from the bucket, not by guessing.
- Glints device verification is a first-class login state: from an untrusted device (the server) the credential submit lands on the "Verifikasi diri Anda" interstitial (`device_verification` in `classifyGlintsLoginResult`, detected by the `send-email/whatsApp-verification-btn` data-cy buttons). The scraper clicks the EMAIL option only — never WhatsApp — then opens a row in `scrape.glints_verification` (service-key-only table, atlas-managed), logs `GLINTS_VERIFICATION_CODE_NEEDED (… row <id>)`, and polls that row for 10 minutes for a human to `UPDATE … SET code='…'`. The code page submits through its **own** button, `[data-cy="otp-verify-btn"]` ("Verifikasi", `GLINTS_VERIFICATION_SUBMIT_SELECTOR`, text-locator fallback) — it has no `button[type="submit"]`, so reusing the credential-login submit selector there silently typed the code and never sent it, mis-settling correct codes as `rejected`; never click the sibling `otp-resend-button-btn`/`otp-back-btn`. Code emails are capped at one per 30 minutes via the row timestamps (durable across restarts); a verification wait or timeout is NOT a failed login attempt, so the cycle keeps re-entering the flow without burning the credential budget. A legacy `otp_required` classification (code input already rendered, or a verification route) still parks the whole budget.
- The direct sink path deliberately does **not** mirror rows into the central Supabase ingestion: `src/central/portalBridge.ts` stays wired only to the legacy SQLite insert path. Do not re-add `ingestPortalApplicant`/`ingestPortalVacancy` calls to the sink path.
- Glints' employer-dashboard UI language is a **per-account server-side setting**, independent of the scraper's pinned `id-ID` browser locale — one live account was observed rendering entirely in English ("Post A Job", "Change", a "NEW" status badge) instead of the Indonesian text every extractor originally assumed ("Pasang Loker", "Ubah", "Belum Sesuai"). `GLINTS_DASHBOARD_MARKER_SELECTOR` and the applicant-modal wait in `ExtractApplicantDetail` (`src/glints.ts`) now match both languages; `waitForDashboardOrLogin`'s timeout fallback also no longer trusts a URL-substring check (an unauthenticated session can land on a marketing page whose URL never contains "/login") and instead requires the dashboard marker itself. If a future account/locale renders yet another language variant, extend those same match sets rather than re-introducing a single-language assumption. `ExtractListVacancyPage` also now returns each vacancy's real Glints `jid` (previously computed then discarded, falling back to a synthesized `sha1(portal+applied_for)` id downstream) — `Glints.sendToSink` writes through the shared `sendApplicantToSink` (`src/portalSink.ts`) contract like every other sink-routed portal instead of its own hand-rolled upsert calls, so `data.contact.type` is `"phone"` (the shared contract's canonical spelling) and `cv`/`photo` no longer appear inside `data` (only as top-level `cv_object_key`/`photo_object_key`), matching kitalulus. `extractName` (`src/glints.ts`) parses the name out of the cell's full text (splitting on the "`<age> yo`" tag or the first "`·`" separator) rather than a fixed `div[1]/span` XPath, which silently returned an unrelated badge's text ("Willing to relocate") once a UI revision moved things around — prefer that resilient-parse pattern over a positional XPath for any other cell whose sub-layout might drift.
- `SupabaseSink.uploadArtifactBytes`/`uploadDebugArtifact` retry a transient 502/503/504 from Supabase Storage a few times (`withTransientRetry`) before giving up — a single gateway blip used to fail the whole applicant row and burn a full `runWithRetry` attempt (fresh browser + re-login) just to redo one upload. Safe because both upload paths are already idempotent (content-addressed or timestamped key, duplicate-tolerant catch). Anything that inspects the caught error for the *duplicate* check must not call `axios.isAxiosError` a second time on the same error in tests that stub it with `mockReturnValueOnce` — `withTransientRetry` duck-types the status instead, precisely to avoid consuming that one-shot mock before the caller's own check runs.
- `scrape.portal_vacancies` rows for `kita_lulus` with a 40-hex-char `portal_vacancy_id` (a SHA1 hash) instead of KitaLulus' own short alphanumeric vacancy id are the fallback path in `sendApplicantToSink` (`src/portalSink.ts`) firing because the row's `vacancy_id` came in empty — `title` on those rows is the candidate's own summary-card text, not a job title. Root-caused against `main@288de3f`: that build's `KitaLulus.sendToSink(param, listPageUrl: string)` never set `vacancy_id` at all (only `vacancy_url: listPageUrl`, the shared pending-applicants list URL) and derived `applied_for` from `extractAppliedForFromRow` — the candidate table row's own cell text — not a real vacancy title. `fm/scraper109-ingestion` fixed this (`sendToSink` now takes a real `OpenVacancy` with a guaranteed non-empty id/title); `tests/portalSendToSink.test.ts`'s "upserts the real vacancy" test pins the invariant. As of 2026-09-08 this pollution was still growing in real time (rows first-seen within the hour, `last_seen_at` refreshing roughly hourly) from a source outside every locally-checked-out branch. Likely culprit: `src/viewer.ts`'s hourly auto-scheduler (`scheduleAll()`/`enableSchedule()`, `POST /api/schedule/enable`, `setInterval(..., 3_600_000)`) spawns `ts-node src/server.ts <portal>` for every entry in `SCRAPERS` against whatever `src/kitalulus.ts` that deployed viewer has checked out — if that's `main` (pre-fix, not yet merged), the cadence matches exactly. Never delete/rewrite these rows without captain approval; classify with `portal_vacancy_id ~ '^[0-9a-f]{40}$'` (matches only the polluted rows — KitaLulus' real ids are short and mixed-case alphanumeric, never 40 lowercase hex chars).
- The mirrored `talent_scraping` tables are populated database-side: a SECURITY DEFINER trigger on `scrape.portal_candidates` (`atlas/migrations/20260818090000_project_talent_scraping.sql`) projects each candidate write. Client code never touches the `talent_scraping` schema and anon has no grants there — do not add client-side writes to it.

## Local smoke-testing the portals

- A fresh worktree has no `.env` (only `.env.sample`), so `SCORING_SUPABASE_URL`/`ANON_KEY`/`SERVICE_KEY` are unset. Glints, Jooble, SEEK, Pintarnya and kitalulus-v1 all call `getSink()` (`new SupabaseSink()`) as the *first* line of `Scrape()` by design ("fail fast... mirrors glints" — see each portal's `Scrape()`), so all five throw `SupabaseSink: SCORING_SUPABASE_URL is required` before launching a browser or attempting login. This is not a portal auth/selector problem; it needs a real `.env` (not committed, and none of the git-ignored runtime files carry it either) before any of those five portals can be smoke-tested end to end.
- kitalulus-v2 is the exception (still on the legacy `api_destination`, no Supabase gate) and does launch a real browser. Its post-login flow assumes an onboarding product tour of exactly 3 "Lanjut" clicks then "OK" (`tooltipsDashbaord`, `src/kitalulus-v2.ts:1253-1261`) and a second tooltip flow of 2 "Lanjut" + "SELESAI" (`tooltipsLowongan`, same file ~1263-1274). A 2026-09-05 smoke run got through login and 2 of the 3 first-tour clicks, then hung on `getByRole('button', { name: 'Lanjut' })` for the full 120s Playwright timeout — i.e. auth succeeded and the dashboard loaded, but the tour selector count no longer matches the live UI. Treat a hang here as tour-selector drift, not a credential problem, and check the click count against the current dashboard before assuming the session is dead.
- SEEK login is recaptcha-gated as of 2026-09-08: a fresh credential login (`loginWithCredentials` in `src/seek.ts`, also the flow `src/seek-auth.ts` drives) submits into a "Please complete the recaptcha." wall from an unrecognised session, so a scripted login cannot get past it — this held for both the credentials committed in `seek.json` and the separate `JOBSTREET_EMAIL`/`PASSWORD` pair in the operator's `scrap.env` (two different SEEK accounts). The committed `seek.json` session cookies were also already expired/invalidated server-side (redirect to `authenticate.seek.com` even before the cookie-expiry filter ran). Refreshing `seek.json` therefore needs a human to run `npm run dev:seek-auth` in a headed browser and solve the recaptcha by hand; there is no known scripted path around it, and none should be built (anti-bot evasion is out of scope). `src/seek.ts` enumerates job ad postings and extracts each one's description via `extractJobPostings`/`extractVacancyDescription` (persisted through `sendVacancyToSink`, independent of any applicant — the same vacancy/candidate separation contract kitalulus established), but the employer dashboard's job-postings-listing route and markup are unverified against a live session for the reason above; `JOB_ADS_URLS` in `src/seek.ts` lists the routes tried in order (overridable via `seek.json`'s `job_ads_urls`), and a run that finds zero postings logs which routes it tried — check that log before assuming the fix regressed. The description selector (`[data-automation="jobAdDetails"]`) is confirmed against SEEK's public `id.jobstreet.com/job/{id}` rendering (same numeric id family the employer dashboard is expected to expose) but not against the employer dashboard itself.
- kitalulus **v1**'s `/vacancy` (Lowongan) listing page has its own separate onboarding tour on a fresh session — 3x "Lanjut" then "SELESAI" then "OK" inside an MUI `role="alertdialog"` — distinct from `tooltipsDashbaord`'s dashboard tour and from `dismissMarketingOverlay`'s "HR LEADER GATHERING" promo; it blocks every click on the page via a full-viewport react-joyride overlay until dismissed through its own buttons (`dismissVacancyListTour` in `src/kitalulus.ts`). Never remove that overlay's DOM node directly to work around it — it's React-owned, and yanking it out from under a live component crashes the SPA's error boundary ("Terjadi Kendala Teknis"). The page also floats a `<getsitecontrol-widget>` "Chat Kandidat" promo with an open shadow root; Playwright's CSS engine pierces it, so its real close button is just `page.locator("button.close")` (`dismissChatWidget`) — no need to reach into the shadow root by hand. See `docs/kitalulus-description-flow.md` for the full list -> detail click-flow these unblock.

## Extraction tooling evaluation

- Crawl4AI and Scrapling were evaluated (bounded, fixture-based) as extraction aids for selector drift and were rejected: both are Python-native (Scrapling has no Node/JS port; the `crawl4ai` npm package is only a REST client for a separately-hosted Python service), and this repo's runtime — `package.json`, and the Playwright+Node-only production `dockerfile` — is 100% Node/TS with no Python anywhere. See `docs/extraction-eval.md` for the fixture comparison (current selector logic vs. Scrapling's adaptive text lookup) and the fixture tests in `tests/kitalulus.unit.test.ts` (`extractVacancyDescription`, `[fixture: ...]` cases) that now track the known drift gap this evaluation examined. Re-run that comparison before reconsidering either library, rather than re-deriving it from scratch.
